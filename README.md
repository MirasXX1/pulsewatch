# PulseWatch

Локальный Uptime Monitor для одного пользователя: Java 21 / Spring Boot / Maven, PostgreSQL и Next.js / TypeScript / Tailwind CSS. Интерфейс на русском, казахском и английском; русский — по умолчанию. Регистрации, оплаты и внешних интеграций нет. Для тестов frontend нужен Node.js 22.12+ (проверено на 24.9.0).

## Запуск на macOS (Apple Silicon)

На проверенном Mac установлены Homebrew, Node.js 24.9.0, Java 21 и Docker Desktop. Maven 3.9.11 найден внутри IntelliJ IDEA; launcher использует его без переустановки. На новой машине setup ниже установит только отсутствующие компоненты. Системные Java 25/26 сохраняются; Java 21 выбирается только для процесса проекта. Порт `5432` уже занят локальным PostgreSQL, поэтому Compose использует `127.0.0.1:5433` (внутри контейнера — `5432`). Существующий PostgreSQL не останавливается.

В обычном Terminal macOS, из корня проекта:

```bash
bash scripts/setup-mac.sh
```

Скрипт проверяет архитектуру `arm64`, сохраняет резервные копии `.zshrc` и `.zprofile` перед установщиками и устанавливает **только отсутствующие** Temurin 21 и Docker Desktop. Node.js и существующий Maven он не переустанавливает. Установщик Java может запросить пароль администратора — введите его в Terminal/системном диалоге.

Когда откроется Docker Desktop, подтвердите macOS Open/«Открыть», если появится, примите условия Docker и завершите стартовую настройку. Дождитесь состояния **Engine running**. Вход в Docker Hub для проекта не требуется.

```bash
bash scripts/run-local.sh check
bash scripts/run-local.sh verify
bash scripts/run-local.sh backend
```

`verify` запускает PostgreSQL, backend-тесты (включая интеграцию с настоящей БД), Maven-сборку, проверку TypeScript и production-сборку frontend. После успешной проверки `backend` запускает Spring Boot на `127.0.0.1:8080` и применяет Flyway-миграцию.

Во **втором терминале**, из папки проекта:

```bash
bash scripts/run-local.sh frontend
```

Откройте **http://127.0.0.1:3000**. Пока оба процесса запущены, в третьем терминале можно проверить реальные API/UI и сохранение истории:

```bash
bash scripts/run-local.sh smoke
```

Smoke-проверка проверяет HTML, favicon, JS/CSS, прямой API и frontend-прокси, создаёт временный монитор `https://example.com`, ждёт первую, ручную и следующую плановую проверку, проверяет историю и долю успешных результатов. Затем удаляет только свои временные мониторы. Ожидание 60-секундного планировщика может занять до 90 секунд. Итог записывается в `.local/verification/smoke.json`. Существующие мониторы не удаляются. Это HTTP-проверка, без автоматизации браузера.

Launcher создаёт `.env` из `.env.example`, **только если файла ещё нет**. Все изменения PATH и выбор Java действуют внутри launcher, без записи в shell-конфигурацию. Frontend проксирует `/api` в backend. `BACKEND_URL` считывается Next.js при запуске/сборке. Spring Boot получает переменные из `.env` через launcher.

Переключатель **RU / KZ / EN** находится в верхней панели. Выбор сохраняется в `localStorage` (`pulsewatch.locale`) и применяется на странице сайта и после перезагрузки. Даты, числа и проценты форматируются по выбранному языку, время — по часовому поясу браузера. Статусы и сообщения API/проверок переводятся только во frontend; исходная история в БД не меняется. Для неизвестной технической ошибки доступен раскрываемый блок с оригиналом.

Создайте монитор, например `Example` → `https://example.com`. Первая проверка запускается сразу; до сохранения результата статус — `PENDING`. Нажмите имя сайта для истории или `Check now` для внеочередной проверки. Удаление требует подтверждения и удаляет историю этого сайта.

Остановка: `Ctrl+C` в обоих терминалах, затем из корня `docker compose stop` (если Docker CLI не попал в PATH, используйте `"$HOME/.docker/bin/docker" compose stop` или `/Applications/Docker.app/Contents/Resources/bin/docker compose stop`). Данные сохраняются в Docker volume; не используйте `down -v`, если хотите оставить историю.

Подробная диагностика Mac и исправление ошибки `compdef` с резервной копией — в [MACOS_SETUP.md](MACOS_SETUP.md).

## Проверки и сборка

Универсальная проверка на этом Mac: `bash scripts/run-local.sh verify`. Ниже — отдельные команды для окружения, где Java 21 и `mvn` уже добавлены в PATH:

```bash
mvn -f backend/pom.xml test
mvn -f backend/pom.xml package
cd frontend
npm test
npm run typecheck
npm run build
npm run check:build
npm start
```

Unit-тесты не требуют PostgreSQL. Они проверяют запрещённые IPv4/IPv6 и форматы URL, смешанные DNS-ответы, повторное DNS-разрешение, HTTP-коды, перенаправления, размер заголовков, отсутствие чтения тела, дедлайн, ограничение рабочих потоков и очереди, запрет параллельной проверки одного сайта и API. Сетевые тесты используют только собственный loopback-сервер с тестовой подменой DNS. Производственная политика адресов не ослабляется. Если sandbox явно запрещает bind сокетов, сетевой класс пропускается с причиной.

Для интеграционных тестов на **настоящем PostgreSQL**, после `docker compose up -d --wait`, в корне:

```bash
export PULSEWATCH_TEST_DB_URL=jdbc:postgresql://127.0.0.1:5433/pulsewatch
export PULSEWATCH_TEST_DB_USER=pulsewatch
export PULSEWATCH_TEST_DB_PASSWORD=local-development-only
mvn -f backend/pom.xml test
```

Если меняли `.env`, подставьте свои значения. Эти тесты создают отдельную случайную схему, применяют SQL миграции и удаляют только эту схему. Проверяются история, реальные доли успешных проверок, сортировка, ограничение последних 100 записей и каскадное удаление. Без `PULSEWATCH_TEST_DB_URL` интеграционный класс пропускается.

## Как устроен мониторинг

- Каждые 60 секунд backend ставит сайты в очередь, отдавая приоритет давно проверенным. Первая проверка и ручная проверка используют тот же механизм. При нагрузке время старта может сдвигаться.
- Максимум 4 проверки одновременно, очередь — 100 заданий; один сайт не может иметь два активных или ожидающих задания. Ручной повтор возвращает HTTP 409. Один процесс backend — намеренное ограничение локальной версии.
- На всю проверку, включая DNS, TLS и цепочку перенаправлений, отведено 15 секунд. TCP connect — до 4 секунд. DNS выполняется в отдельном пуле из 4 потоков без неограниченной очереди. Если системный DNS завис, число занятых потоков остаётся ограниченным.
- Допускаются только HTTP/HTTPS без credentials и fragment. Loopback, private, link-local, multicast, unspecified, CGNAT, документационные и зарезервированные адреса блокируются; IPv6 — только обычный global unicast, без переходных/служебных диапазонов. Политика намеренно консервативна.
- Проверяются **все** DNS-адреса назначения. Соединение открывается с конкретным проверенным IP, без второго разрешения имени. Это предотвращает DNS rebinding между валидацией и подключением. Для каждого перехода проверка повторяется; максимум 5 redirects.
- HTTPS использует стандартное хранилище доверия JVM, проверку сертификата и hostname. Host/SNI остаются исходными. Системные HTTP-прокси не используются.
- Используется GET, читаются только заголовки (максимум 32 KiB на один ответ, включая промежуточные 1xx), затем соединение закрывается. Тело не загружается приложением. HTTP 200–399 → `UP`, остальные ответы и ошибки → `DOWN`. Запрещённый redirect или исчерпание лимита также → `DOWN` с причиной.
- В PostgreSQL сохраняются время начала, результат, HTTP-код при его наличии, полная длительность и ошибка. При отсутствии HTTP-ответа код — `null`.
- `Successful checks` — **число сохранённых UP / число всех сохранённых проверок × 100%**. Это доля успешных проверок, а не доступность, взвешенная по времени. Без истории отображается `—`, а не выдуманные 100%.
- Frontend обновляет реальные данные каждые 5 секунд. История страницы ограничена последними 100 результатами; процент учитывает всю историю. Все времена отображаются в часовом поясе браузера.

Структура: `backend/` — API, URL-политика, мониторинг, миграция и тесты; `frontend/` — dashboard и страница сайта; `compose.yaml` — PostgreSQL. Таблицы `sites` и `checks` связаны внешним ключом `ON DELETE CASCADE`, история индексирована по сайту и времени.

API: `GET/POST /api/sites`, `GET/DELETE /api/sites/{id}`, `POST /api/sites/{id}/check`, `GET /api/sites/{id}/checks`. Ручная проверка возвращает `202 Accepted`; результат сохраняется асинхронно. Статус сайта — последний сохранённый результат, флаг `checking` отображает текущую работу.

## Favicon и сборка frontend

Собственная иконка — `frontend/app/icon.svg`: зелёная линия пульса на тёмном фоне. Next.js App Router автоматически создаёт `/icon.svg` и `<link rel="icon">`; ручных `metadata.icons`, других favicon или web manifest нет. Проверка `npm run check:build` подтверждает ровно одну иконку в HTML и наличие её маршрута.

Dev-сервер использует `.next`, а production-сборка и `npm start` — `.next-build`. Эти каталоги разделены, чтобы `npm run build` не перезаписывал JS/CSS и манифесты работающего `npm run dev`. Если dev-сервер открыт при изменении `next.config.ts`, Next.js должен автоматически перезапуститься; при необходимости остановите только frontend через `Ctrl+C` и запустите `bash scripts/run-local.sh frontend` снова. Данные БД не затрагиваются.

Механизмы: [App Router icons](https://nextjs.org/docs/app/api-reference/file-conventions/metadata/app-icons), [Next.js distDir](https://nextjs.org/docs/app/api-reference/config/next-config-js/distDir).

## Проверено в среде разработки агента

- Java-код и тесты скомпилированы и запущены на **Temurin Java 21**. Через локальный JUnit Jupiter engine прошли **75 тестов** URL-политики, планировщика и API.
- **10 frontend-тестов** (`npm test`) прошли. Реальные React-компоненты выполняются в jsdom; HTTP заменён тестовыми фикстурами. Проверены формы, статусы, ручной запуск, история, поиск, удаление/отмена, ошибки, языки/даты, сохранение выбора, а также защита от устаревших ответов и исчезновения ошибок при фоновом обновлении. Эти тесты не подменяют данные работающего приложения.
- Production-сборка `npm run build` прошла с проверкой TypeScript. `npm run check:build` подтвердил русский HTML, ровно одну SVG-иконку, отсутствие конфликтующих favicon, наличие всех 12 ссылающихся JS/CSS-ресурсов и разделение dev/build-каталогов.
- Docker Desktop, Java 21, PostgreSQL на `5433`, backend на `8080` и frontend на `3000` теперь присутствуют на Mac. Наличие слушающих процессов само по себе не доказывает исправность HTTP-ответов.
- Полный Maven test lifecycle **не завершён**: отсутствует кэшированный `surefire-junit-platform:3.2.5`, скачивание Maven Central из sandbox недоступно. Это ограничение окружения, не результат пройденного `mvn test`.
- Живые сетевые и PostgreSQL integration tests, настоящий браузер и полный end-to-end сценарий **не подтверждены**: sandbox запрещает соединения с localhost/Docker socket и bind тестовых сокетов. Попытка live smoke завершилась `Operation not permitted`; не выдаётся за успешную проверку сайта.

Подробный отчёт и точные ограничения — в [VERIFICATION.md](VERIFICATION.md). Для проверки живых сервисов вне sandbox: `bash scripts/run-local.sh verify`, затем при обоих запущенных приложениях `bash scripts/run-local.sh smoke`.

Проект не опубликован; frontend, backend и PostgreSQL настроены на loopback.
